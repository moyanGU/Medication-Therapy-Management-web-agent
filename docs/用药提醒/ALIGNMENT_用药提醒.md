任务名：用药提醒-手机端系统级提醒/闹钟接入

一、项目上下文分析
- 前端：Vue 3 + Vite，Pinia 状态管理；src/pages/reminders/* 与 src/stores/reminder.ts、src/services/reminderService.ts 已有用药提醒的列表/详情/创建/编辑与统计。
- 通知：目前 notificationService.ts 使用浏览器 Notification API 即时弹窗，无法在应用关闭或后台时按时触发系统级提醒。
- 后端：已存在提醒相关接口（/reminders/、/reminder-history/ 等），返回数据遵循 {success, data} 双层结构；可作为设备本地调度数据源。
- 运行环境：Web/PWA 为主；若需系统级闹钟/通知，需要原生能力（Android/iOS）。

二、原始需求
目标：在用户手机端“调用手机中的闹钟功能”，按时提醒服药，具备稳定可靠的到点提醒能力，即使应用被关闭或在后台也能正常提醒。

三、任务边界与约束（初版）
- 可靠性：必须在应用不前台时仍能提醒；尽量具备声音/震动。
- 跨平台：Android 与 iOS 都需要支持；但两者的系统闹钟能力开放度不同，iOS 不提供直接设置系统闹钟的公共接口。
- 体验：允许用户启停提醒、修改时间与频率、支持重复、可选择“稍后提醒/已服用”等交互。
- 数据一致性：提醒计划的主数据由后端维护，设备侧做本地调度与状态反馈（响应/跳过等）。
- 安全与风控：限频、安静时段策略、权限引导、避免滥用通知；遵循现有项目返回结构。

四、现状评估与可行方案
- 纯 Web/PWA：只能依靠 Web Push 或浏览器通知，无法保证到点后台触发，受浏览器与操作系统约束，可靠性不足。
- 原生封装（建议方案）：引入 Capacitor（官方）并集成 @capacitor/local-notifications，本地调度到点通知，跨 Android/iOS，支持重复与时间指定；Android 可进一步探索 Intent 设置系统闹钟，但属平台定制且非官方统一能力。
- 日历回退：生成 ICS 日历事件交给系统日历管理重复提醒，需用户确认添加，体验与一致性受限。

五、初步技术策略（建议）
1) 确定采用 Capacitor 封装移动端能力：
   - 使用 @capacitor/local-notifications 安排本地通知；调用官方 API 的 at/on/every/repeats 组合，实现每天固定时刻或每周指定日重复提醒。
   - 设备侧与后端同步提醒计划；前端在 create/update/toggle 时更新本地调度。
   - Android 端可选增强：通过第三方插件或 Intent 调起系统闹钟设置页（仅用于辅助，主提醒仍以本地通知保障可靠性）。
2) PWA 保留：当在浏览器环境访问时，继续使用 notificationService 即时通知，并给出“安装 App 获得系统级到点提醒”的引导。
3) 数据同步与契约：新增“设备同步”接口，拉取用户有效提醒计划，包含时间/重复/时区等；设备上报响应记录与状态。

六、关键问题清单（待确认）
1) 目标平台：是否同时支持 Android 与 iOS？是否允许发布为移动 App（Capacitor 打包）？
2) 到点提醒强度：是否必须声音提醒（受系统设置影响，如静音/勿扰模式）？是否需要精确到点（Android 13+ exact notifications 设置要求）？
3) 频率模型：每天固定时刻、每周指定日、多时段/多药品如何组合；是否需要“提前 X 分钟提醒”“重复提醒 N 次，每次间隔 M 分钟”？
4) 权限引导：首次安装是否弹权限说明；是否需要在设置页展示通知权限状态与开启指引？
5) 时区与跨日处理：出国或切换时区时提醒是否自动调整；深夜跨日的边界如何处理？
6) 数据一致性：本地调度与后端计划如何冲突解决（例如用户在设备上停用提醒，后端仍为启用）？以哪一侧为准？
7) 风控策略：限频、防止重复/过度提醒；安静时间策略是否需要（例如 22:00-08:00 静音或仅震动）？
8) 交互与反馈：通知动作“已服用/稍后提醒/跳过”是否回写后端；是否统计依从率与响应时间？

七、验收标准（草案）
- 在 Android/iOS 真机上，应用关闭或后台时，到点仍能提醒（震动/声音/横幅）。
- 支持每天固定时刻与每周指定日的重复提醒；允许用户启停与修改。
- 通知点击可跳转至提醒详情；可选择“已服用/稍后/跳过”，结果写入后端历史。
- 设置页可查看权限状态与引导开启；日志可见关键节点（调度创建、触发、响应）。
- PWA 环境下提供能力降级与安装引导，不影响 Web 使用。
