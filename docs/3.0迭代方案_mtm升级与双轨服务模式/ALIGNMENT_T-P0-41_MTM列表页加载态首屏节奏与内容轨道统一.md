# ALIGNMENT_T-P0-41_MTM列表页加载态首屏节奏与内容轨道统一

## 一、原始任务

任务来源：

- 基于已完成的 `T-P0-40 MTM 列表页异常态首屏节奏与内容轨道统一`

当前继续方向：

- 让加载态首屏与空态、异常态更接近同一套页面节奏
- 让列表页在“正在加载”时不再停留在最早期的极简过渡态样式

---

## 二、当前项目理解

### 2.1 当前已具备的能力

当前 `MtmServiceCasesPage.vue` 已经完成：

- 主结果区与空态区的主要展示层已经收口
- 异常态首屏的内容轨道和节奏已经回到同一套页面表达
- 列表页大部分状态分支已经具备统一的首屏说明感

因此当前剩余的最小展示不一致点主要落在 loading 分支：

- loading 仍保留 `p-8` 的旧式简版占位节奏
- 只有一个转圈和一行提示，内容轨道不明显
- 在“加载中 / 加载失败 / 空态”之间切换时，loading 最像另一种旧状态

### 2.2 为什么这是 `T-P0-41` 最合理的最小范围

在 `T-P0-40` 已经补齐异常态后，当前列表页展示层继续小步推进时，最自然的一步就是补齐 loading 分支：

- loading 是最后一个仍未统一的状态分支
- 它仍属于首屏说明型状态
- 只要收口 loading，页面状态分支的展示层就更接近完整闭环

因此本轮最合理的最小范围是：

- 只处理 loading 分支的首屏节奏与内容轨道
- 只改模板结构和样式类，不改加载逻辑
- 不改异常态、空态、主结果区、接口、路由、分页和 `src/utils/mtm.ts`

### 2.3 当前项目的真实使用场景

当前 MTM 列表页仍以患者端浏览为主，因此本轮更适合：

- 让加载态也遵循“当前正在发生什么”的统一表达
- 让用户在状态切换中始终停留在同一套页面体系里

而不是：

- 改请求逻辑
- 改加载文案来源
- 改接口行为

## 三、现有代码约束

### 3.1 当前模板约束

当前状态分支主要包括：

1. loading
2. loadError
3. empty
4. non-empty list

其中 `loading` 当前结构已具备：

- 加载动画
- 一行提示文案

最小改法应是：

- 保留现有顺序和含义
- 只收口 loading 首屏的宽度、间距和节奏
- 不新增新的业务状态层

### 3.2 当前状态约束

本轮必须继续复用现有状态：

- `loading`

也就是说，本轮可以改的是：

- loading 外层内容轨道
- 转圈容器与文本间距
- 首屏整体节奏

不应改动：

- 加载逻辑
- 请求行为
- 其他状态分支逻辑

### 3.3 当前范围约束

根据当前阶段目标，本轮必须严格保持：

- 只改 `src/pages/MtmServiceCasesPage.vue`
- 不改接口
- 不改路由
- 不改 `src/utils/mtm.ts`
- 不改异常态、空态、主结果区、列表项卡片、底部分页条、首页和详情页

## 四、需求边界确认

### 4.1 本任务要做什么

本任务负责：

- 收口加载态首屏节奏与内容轨道
- 让 loading 与异常态、空态更像同一套页面表达
- 保持当前加载逻辑和文案不变
- 补充本轮对齐、共识、验收文档

### 4.2 本任务不做什么

本任务不负责：

- 修改加载逻辑
- 修改提示文案来源
- 修改异常态、空态和主结果区逻辑
- 修改接口、路由和 query 参数
- 修改分页和列表数据流

---

## 五、关键歧义与当前判断

### 5.1 是否需要新增骨架屏

当前判断：

- 不需要

原因：

- 本轮是最小展示层收口
- 引入骨架屏会扩展到新的交互表达方案

### 5.2 是否需要把 loading 改成和空态完全一样

当前判断：

- 不需要

原因：

- loading 仍应保留明显的“处理中”动态语义
- 只需统一轨道和节奏，不必完全同构

### 5.3 是否需要调整提示文案

当前判断：

- 不需要

原因：

- 当前问题主要在展示节奏
- 文案职责已足够清晰

---

## 六、建议实现边界

### 6.1 前端修改内容

建议只修改：

- `src/pages/MtmServiceCasesPage.vue`

### 6.2 建议最小实现方式

建议直接在 loading 模板样式类上做最小调整：

1. 让 loading 外层与空态、异常态接近同一内容轨道
2. 收口转圈与文案之间的间距
3. 保持动态加载语义不变

### 6.3 建议交付表现

本轮页面首版建议具备：

1. 加载态首屏更像当前页面体系内的说明状态
2. 状态切换时视觉落差进一步减小
3. 业务逻辑和文案保持原样，仍然小步、可回滚

---

## 七、风险点

### 7.1 把 loading 做得过重

如果让 loading 过于像完整卡片：

- 会增加等待态的视觉负担

因此本轮只做轻量收口，不抬高其存在感。

### 7.2 扩展到新的加载方案

如果顺手引入 skeleton 或更多占位块：

- 会超出本轮冻结范围

因此本轮只改当前 loading 分支。

### 7.3 削弱动态语义

如果为了统一而过度平化 loading：

- 会让“正在加载”不够直观

因此本轮保留转圈和动态感。

---

## 八、当前结论

`T-P0-41` 最合理的最小范围确定为：

- `MTM 列表页加载态首屏节奏与内容轨道统一`

推荐实现方向：

1. 不改任何加载逻辑、请求行为和数据流
2. 不改接口、路由、异常态、空态和工具函数
3. 仅在 `MtmServiceCasesPage.vue` 中收口 loading 首屏的内容轨道与间距节奏
4. 让列表页状态分支的展示层形成更完整闭环
