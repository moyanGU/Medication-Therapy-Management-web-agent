# ALIGNMENT_T-P0-38_MTM列表页主结果区底部结果说明条阅读轨道收口

## 一、原始任务

任务来源：

- 基于已完成的 `T-P0-37 MTM 列表页空态动作区内容轨道统一`

当前继续方向：

- 让主结果区底部“结果说明 + 分页状态”这一条的阅读轨道更清晰
- 让结果说明与分页状态的主次关系更稳定，不再只是左右并排的信息拼接

---

## 二、当前项目理解

### 2.1 当前已具备的能力

当前 `MtmServiceCasesPage.vue` 已经完成：

- 主结果区顶部摘要卡的阅读节奏已经收口
- 空态顶部说明与空态动作区的内容轨道已经统一
- 主结果区底部已经具备 `resultSectionCopy` 和 `resultPageStatus` 两块明确职责

因此当前残留的问题主要落在主结果区底部说明条本身：

- 左侧结果说明仍是整块自然撑开，阅读轨道不够明确
- 右侧分页状态虽然已收口成唯一展示位，但视觉上仍像普通文本
- 两者并排后，主说明和辅助状态的层级差异还不够稳定

### 2.2 为什么这是 `T-P0-38` 最合理的最小范围

前几轮已经分别收口了：

- 顶部摘要卡语义与节奏
- 空态顶部与空态动作区轨道

当前最自然的一步，不是再改空态，也不是动列表项，而是只处理主结果区底部说明条：

- 左侧保持为主结果说明
- 右侧继续作为辅助分页状态
- 两者在同一条说明条里形成更稳定的主次关系

因此本轮最合理的最小范围是：

- 只处理主结果区底部说明条的阅读宽度、间距和辅助状态表现
- 只改模板结构和样式类，不改任何 `computed`
- 不改空态区、顶部摘要卡、接口、路由、分页逻辑和 `src/utils/mtm.ts`

### 2.3 当前项目的真实使用场景

当前 MTM 列表页仍以患者端浏览和判断下一步为主，因此本轮更适合：

- 让用户更快扫到左侧主说明
- 让用户把右侧分页状态理解为辅助信息，而不是并列正文

而不是：

- 改分页行为
- 改结果说明文案
- 改列表项卡片布局

## 三、现有代码约束

### 3.1 当前模板约束

当前主结果区底部说明条主要由两部分组成：

1. 左侧 `resultSectionCopy`
2. 右侧 `resultPageStatus`

当前问题点在于：

- 左侧没有明显的阅读轨道约束
- 右侧虽然右对齐，但视觉重量与辅助定位还不够清晰

最小改法应是：

- 保留“左主右辅”的现有结构
- 只收口宽度、间距和容器层级
- 不新增新的状态层

### 3.2 当前状态约束

本轮必须继续复用现有状态：

- `resultSectionCopy`
- `resultPageStatus`

也就是说，本轮可以改的是：

- 左侧说明块的阅读宽度
- 右侧分页状态的容器表现
- 两者之间的视觉间距与对齐方式

不应改动：

- `resultSectionCopy` 文案逻辑
- `resultPageStatus` 文案逻辑
- 分页按钮和分页行为

### 3.3 当前范围约束

根据当前阶段目标，本轮必须严格保持：

- 只改 `src/pages/MtmServiceCasesPage.vue`
- 不改接口
- 不改路由
- 不改 `src/utils/mtm.ts`
- 不改空态区、顶部摘要卡、列表项卡片、底部分页条、首页和详情页

## 七、风险点

### 7.1 过度强调右侧分页状态

如果把右侧块做得太重：

- 会抢走左侧主说明的注意力

因此本轮只做轻量辅助块，不抬升为主内容。

### 7.2 左侧宽度收得太狠

如果左侧说明轨道压得太窄：

- 会导致描述换行过多

因此本轮只做适度收口，不追求极限紧凑。

### 7.3 范围扩到分页交互区

如果顺手改到底部分页按钮条：

- 会超出本轮冻结范围

因此本轮只处理说明条本身。

---

- `MTM 列表页主结果区底部结果说明条阅读轨道收口`

推荐实现方向：

1. 不改任何 `computed`、分页逻辑和动作行为
2. 不改接口、路由、空态区和工具函数
3. 仅在 `MtmServiceCasesPage.vue` 中收口底部说明条的左侧阅读轨道与右侧辅助状态表现
4. 让主结果区底部说明条的主次层级更稳定
