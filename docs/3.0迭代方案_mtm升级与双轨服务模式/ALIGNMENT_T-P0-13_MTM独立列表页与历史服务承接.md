# ALIGNMENT_T-P0-13_MTM独立列表页与历史服务承接

## 一、原始任务

任务来源：

- 基于已完成的 `T-P0-11 MTM 最小详情展示与首页状态跳转`
- 基于已完成的 `T-P0-12 MTM 详情页最小状态推进`

当前继续方向：

- 为 MTM 服务单补一个独立列表页
- 承接首页最近 3 条之外的历史服务单
- 让用户可以集中查看自己参与过的全部专业服务，并继续进入详情

---

## 二、当前项目理解

### 2.1 当前已具备的能力

当前项目已经具备：

- 首页发起 MTM 服务单
- 首页展示最近 3 条 MTM 服务状态
- 首页进入 MTM 详情页
- 详情页查看摘要
- 详情页最小状态推进
- 后端分页列表接口 `GET /api/mtm/service-cases/`

因此当前真正缺的，不是新的 MTM 业务能力，而是：

- 一个承接更多历史服务单的独立页面
- 一个比首页最近 3 条更完整的浏览入口

### 2.2 为什么这就是 `T-P0-13` 最合理的最小范围

当前链路已经做到：

- 可创建
- 可查看详情
- 可最小推进状态

但仍存在两个明显缺口：

- 首页只能看最近 3 条
- 历史服务单缺少集中浏览页

如果下一步直接做：

- 药师工作台
- 列表页批量操作
- 复杂筛选面板

会把任务扩大到新的页面体系。

因此当前最合理的最小范围是：

- 新增“我的专业服务”列表页
- 提供最小搜索、状态筛选、分页和进入详情能力

### 2.3 当前项目的真实使用场景

当前项目仍以患者端自助查看为主，不是药师中后台。

因此本轮列表页更适合定位为：

- 我的专业服务历史
- 查看服务进度与结果
- 继续进入详情

而不是：

- 药师工作队列
- 多角色协作管理页

## 三、现有代码约束

### 3.1 后端接口约束

当前后端列表接口已经支持：

- 分页
- `status` 筛选
- `trigger_source` 筛选
- `search`
- 排序

因此本轮原则上不新增新的后端列表接口，优先复用：

- `GET /api/mtm/service-cases/`

### 3.2 首页承接约束

当前首页 MTM 区块已经具备：

- 最近服务状态列表
- 查看当前详情

因此本轮最小承接动作应该是：

- 在首页 MTM 区块补“查看全部”

而不是重构首页布局。

### 3.3 列表页交互约束

当前项目已有列表页模式通常包括：

- 页头说明
- 搜索与筛选
- 加载态 / 错误态 / 空态
- 卡片或表格列表
- 分页

因此 MTM 列表页应延续现有项目风格，不单独发明复杂交互框架。

### 3.4 响应结构约束

当前项目前端必须继续正确处理：

- `{ success, data, message }`
- 分页列表的双层 `data` 解包

因此本轮 MTM 列表页必须继续复用现有 `api` 工具和 `mtmApi.getServiceCases()`。

## 四、需求边界确认

### 4.1 本任务要做什么

本任务负责：

- 新增 MTM 独立列表页
- 新增列表页路由
- 扩充 MTM 列表查询参数定义
- 在列表页展示服务单列表、状态、触发来源、时间和详情入口
- 支持最小搜索、状态筛选和分页
- 在首页 MTM 区块新增“查看全部”入口
- 补充本轮对齐、共识、验收文档

### 4.2 本任务不做什么

本任务不负责：

- 新增后端接口
- 新增药师工作台
- 新增批量操作
- 新增复杂高级筛选
- 新增创建服务单表单页
- 新增编辑问诊/评估/计划/随访能力

这些内容超出“独立列表页与历史服务承接”的范围。

---

## 五、关键歧义与当前判断

### 5.1 是否需要单独创建入口

当前判断：

- 列表页不单独新增正式创建逻辑

建议：

- 引导用户回首页创建

原因：

- 首页已完成未完成服务单防重复创建逻辑
- 避免在列表页重复复制一套创建判断

### 5.2 是否需要复杂筛选

当前判断：

- 首版只做最小搜索和状态筛选

原因：

- 已足够承接历史服务浏览
- 不必把首版做成重型后台筛选器

### 5.3 是否需要触发来源筛选

当前判断：

- 首版可以先不单独暴露

原因：

- 用户更关心当前进度和服务名称
- 状态筛选的优先级更高

### 5.4 列表样式用表格还是卡片

当前判断：

- 更适合用卡片式列表

原因：

- 当前 MTM 信息偏摘要、偏进度，不是密集数据表
- 与首页和详情页风格更一致

### 5.5 列表页放在哪个路由

当前判断：

- 新增路由 `/mtm/service-cases`

原因：

- 与详情路由 `/mtm/service-cases/:id` 成对出现
- 路由语义清晰

## 七、风险点

### 7.1 任务扩大为完整后台列表

如果本轮继续追加：

- 多条件筛选
- 排序控制面板
- 批量流转
- 批量导出

会导致范围失控。

### 7.2 列表页与首页信息不一致

如果状态文案、触发来源文案和时间说明各写各的：

- 用户体验会割裂

因此本轮应继续复用 `src/utils/mtm.ts`。

### 7.3 分页与筛选未联动

如果切换筛选后仍停留旧页码：

- 很容易出现“看起来没有数据”的误判

因此首版应在切换筛选时重置到第一页。

---

## 八、当前结论

`T-P0-13` 最合理的最小范围确定为：

- `MTM 独立列表页与历史服务承接`

推荐实现方向：

1. 不新增后端接口
2. 复用 `/api/mtm/service-cases/`
3. 新增独立列表页 `/mtm/service-cases`
4. 在首页最近服务状态区补“查看全部”
5. 以“能浏览、能筛选、能翻页、能进详情”为本轮交付目标
