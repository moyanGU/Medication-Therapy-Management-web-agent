# ALIGNMENT_T-P0-16_MTM列表页首页入口参数联动与快捷筛选跳转

## 一、原始任务

任务来源：

- 基于已完成的 `T-P0-15 MTM 列表页触发来源筛选与排序保持`

当前继续方向：

- 让首页 MTM 区块进入列表页时可以直接带预设参数
- 让首页提供最小快捷筛选跳转，而不是只进入一个“空白列表”

---

## 二、当前项目理解

### 2.1 当前已具备的能力

当前项目已经具备：

- 首页 MTM 建议区块
- 首页最近 3 条 MTM 服务状态
- MTM 独立列表页
- 列表页支持：
  - `status`
  - `trigger_source`
  - `ordering`
  - URL 查询保持
- 详情页返回列表时恢复筛选上下文

因此当前真正缺的，不是新的列表能力，而是：

- 首页入口到列表页的参数联动
- 首页当前上下文到列表页的快捷筛选承接

### 2.2 为什么这是 `T-P0-16` 最合理的最小范围

当前列表页本身已经可以：

- 搜索
- 筛选
- 排序
- 保持 URL

但从首页进入列表页时仍然只有：

- 纯粹的“查看全部”

这意味着首页虽然知道：

- 当前有无进行中服务
- 当前建议发起的触发背景
- 最近服务状态

却没有把这些上下文真正传给列表页。

因此当前最合理的下一步是：

- 让首页入口变成“带上下文进入列表页”
- 让用户一跳就落到最相关的服务子集

### 2.3 当前项目的真实使用场景

当前项目仍以患者端自助浏览为主。

因此首页快捷跳转更适合用于：

- 直接看当前阶段的服务
- 直接看与当前建议原因同类的服务
- 直接看全部历史服务

而不是：

- 做复杂运营看板
- 做药师工作队列分流

## 三、现有代码约束

### 3.1 首页 MTM 上下文约束

当前 `DashboardPage.vue` 已经具备：

- `activeMtmCase`
- `recentMtmCases`
- `buildMtmTriggerSource()`
- `mtm_entry_hint`

因此本轮无需新增新的首页接口字段，应直接复用这些现有上下文。

### 3.2 列表页查询参数约束

当前列表页已支持并保持：

- `page`
- `search`
- `status`
- `trigger_source`
- `ordering`

因此本轮首页到列表页的快捷跳转必须优先复用这些现有参数，而不是新造：

- `preset`
- `scene`
- `mode`

之类的临时字段。

### 3.3 详情页返回约束

当前详情页已经能恢复列表查询上下文。

因此只要首页进入列表页时使用正式 query 参数：

- 后续从列表再进详情，返回链路就天然成立

这意味着本轮不需要额外修改详情页逻辑。

### 3.4 页面复杂度约束

当前首页 MTM 区块已经有：

- 操作按钮
- 最近服务状态

因此本轮更适合：

- 在现有 MTM 区块中补少量快捷入口

而不是：

- 新增新的首页模块
- 改造常用入口整块结构

---

## 四、需求边界确认

### 4.1 本任务要做什么

本任务负责：

- 首页“查看全部”入口改为参数化跳转列表页
- 首页 MTM 区块增加最小快捷筛选入口
- 快捷入口复用现有列表页 query 参数
- 保持和列表页、详情页现有 query 联动兼容
- 补充本轮对齐、共识、验收文档

### 4.2 本任务不做什么

本任务不负责：

- 新增后端接口
- 修改列表页筛选模型
- 修改详情页返回机制
- 重构首页整体布局
- 在首页加入复杂筛选面板

这些内容超出“首页入口参数联动与快捷筛选跳转”的范围。

---

## 五、关键歧义与当前判断

### 5.1 首页要暴露哪些快捷跳转

当前判断：

- 首版只做最自然的 2 类：
  - 当前阶段服务
  - 同类触发服务

原因：

- 都能直接复用首页现有上下文
- 数量少，用户好理解

### 5.2 “查看全部”要不要继续保持全量

当前判断：

- 要

但建议：

- 默认带 `ordering=-created_at`

原因：

- “查看全部”仍应代表完整列表
- 只是明确以最近创建优先进入

### 5.3 当前阶段服务怎么映射

当前判断：

- 如果存在 `activeMtmCase`
- 则快捷跳转使用其当前 `status`

原因：

- 这是首页最明确、最真实的当前上下文
- 不需要人为再定义“进行中”的复合筛选语义

### 5.4 同类触发服务怎么映射

当前判断：

- 复用现有 `buildMtmTriggerSource()`

原因：

- 该函数已经被首页发起 MTM 服务逻辑使用
- 能与首页当前建议原因保持一致口径

### 5.5 是否要在常用入口区再加一个 MTM 列表入口

当前判断：

- 首版不做

原因：

- 当前 MTM 区块已经是最自然的承接位置
- 不需要把同类入口分散到首页多个区域

## 六、建议实现边界

### 6.1 前端修改内容

建议修改：

- `src/pages/DashboardPage.vue`

### 6.2 首页 MTM 区块新增能力

首页 MTM 区块首版建议具备以下能力：

1. “查看全部”带默认排序进入列表页
2. 当前有进行中服务时，可跳到该状态对应列表
3. 当前存在建议原因时，可跳到同类触发来源列表
4. 快捷入口命名清晰、可读

---

## 七、风险点

### 7.1 首页入口新增太多导致信息过载

如果一次补太多跳转：

- 首页会显得拥挤
- 用户难以理解哪个入口最适合自己

因此本轮必须控制入口数量。

### 7.2 首页使用了列表页未支持的参数

如果首页拼出列表页不认识的 query：

- 会导致跳转行为不一致

因此首页必须只复用现有正式参数：

- `status`
- `trigger_source`
- `ordering`

### 7.3 首页和列表页默认排序口径不一致

如果首页“查看全部”与列表页默认顺序不一致：

- 用户可能误以为数据排序异常

因此本轮应保持“最近创建优先”口径一致。

---

## 八、当前结论

`T-P0-16` 最合理的最小范围确定为：

- `MTM 列表页首页入口参数联动与快捷筛选跳转`

推荐实现方向：

1. 不新增后端接口
2. 首页仅复用现有列表 query 参数
3. 在首页 MTM 区块补最小快捷筛选跳转
4. “查看全部”继续保留，但改为参数化进入
5. 以“从首页一跳就进入最相关的 MTM 列表结果”为本轮交付目标
