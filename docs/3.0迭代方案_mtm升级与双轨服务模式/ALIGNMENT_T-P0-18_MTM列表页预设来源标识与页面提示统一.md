# ALIGNMENT_T-P0-18_MTM列表页预设来源标识与页面提示统一

## 一、原始任务

任务来源：

- 基于已完成的 `T-P0-17 MTM 首页常用入口与列表页快捷预设统一`

当前继续方向：

- 让 MTM 列表页知道自己是从哪个首页预设入口进入的
- 让列表页顶部的人话提示和首页预设口径保持一致

---

## 二、当前项目理解

### 2.1 当前已具备的能力

当前项目已经具备：

- 首页 MTM 入口预设统一
- 首页 MTM 区块快捷跳转
- 首页“常用入口”中的 MTM 主入口
- MTM 列表页支持：
  - `status`
  - `trigger_source`
  - `ordering`
  - URL 查询保持

因此当前真正缺的，不是新的筛选能力，而是：

- 列表页无法识别“自己是从哪个预设入口来的”
- 列表页顶部文案还不知道该按哪个首页预设语义提示用户

### 2.2 为什么这是 `T-P0-18` 最合理的最小范围

当前首页已经可以把用户送到更相关的列表结果，但列表页仍然只知道：

- 当前有哪些 query 参数

却不知道：

- 这些参数是用户手动筛出来的
- 还是首页某个快捷预设直接带过来的

这会带来两个体验断点：

- 用户进入列表页后，不清楚自己是从哪个首页入口来到这里
- 页面提示文案无法与首页入口名称保持一致

因此当前最合理的最小范围是：

- 为首页预设入口补正式来源标识
- 让列表页用这个标识展示统一提示

### 2.3 当前项目的真实使用场景

当前项目仍以患者端的人话导航为主。

因此本轮最适合：

- 给列表页补清晰来源提示
- 强化“我为什么会来到这里”的可理解性

而不是：

- 增加更多筛选器
- 增加复杂的预设管理系统

## 三、现有代码约束

### 3.1 当前首页预设约束

当前 `buildMtmListPresetEntries()` 已经能返回：

- `title`
- `shortLabel`
- `description`
- `to`

但当前 `to` 里只包含列表页筛选和排序参数，不包含正式的预设来源标识。

因此本轮应继续扩展这套 helper，而不是在首页页面里临时拼一个新参数。

### 3.2 当前列表页约束

当前 `MtmServiceCasesPage.vue` 只能解析：

- `page`
- `search`
- `status`
- `trigger_source`
- `ordering`

因此它无法知道：

- 当前结果是否来自首页预设
- 如果来自预设，应该用哪套人话提示

### 3.3 当前详情页约束

当前详情页返回列表时已经会恢复列表查询上下文。

因此如果本轮把“预设来源标识”放进正式 query：

- 列表页进入详情再返回时，这个标识也应继续被恢复

### 3.4 参数复杂度约束

当前我们已经明确不新增：

- `scene`
- `mode`
- 一堆临时参数

因此本轮应只新增一个正式且可解释的预设来源标识，不做多层来源体系。

## 四、需求边界确认

### 4.1 本任务要做什么

本任务负责：

- 为首页 MTM 预设入口增加正式来源标识
- 列表页解析并识别该标识
- 列表页顶部增加预设来源提示
- 页面提示文案与首页统一预设口径保持一致
- 列表进入详情再返回时继续保留该标识
- 补充本轮对齐、共识、验收文档

### 4.2 本任务不做什么

本任务不负责：

- 新增后端接口
- 修改列表页筛选模型
- 修改首页布局结构
- 增加更多预设类型
- 增加复杂来源追踪系统

这些内容超出“预设来源标识与页面提示统一”的范围。

---

## 五、关键歧义与当前判断

### 5.1 来源标识用什么字段名

当前判断：

- 使用单一正式字段，例如：
  - `preset_source`

原因：

- 语义直白
- 不和现有后端筛选参数冲突
- 能明确表达“这是首页预设带来的列表来源”

### 5.2 来源标识取值用什么

当前判断：

- 直接复用现有预设 key：
  - `all`
  - `active_status`
  - `suggested_trigger`

原因：

- 与首页共享预设 helper 天然一致
- 无需再引入第二套映射表

### 5.3 列表页提示放在哪里

当前判断：

- 放在列表页页头区域

建议形式：

- 一个小提示条或说明块
- 展示“你当前来自哪个首页快捷入口”

原因：

- 用户一进页面就能看到
- 不会干扰列表本身内容

### 5.4 用户手动修改筛选后，来源标识要不要保留

当前判断：

- 首版在用户主动改筛选、排序、搜索时清除来源标识

原因：

- 避免列表页还显示旧的来源提示，造成误导
- 让页面提示只对真实预设进入场景负责

### 5.5 详情返回是否恢复来源标识

当前判断：

- 要

原因：

- 否则从列表进入详情再返回时，列表页顶部提示会丢
- 会破坏“来源提示连续性”

## 六、建议实现边界

### 6.1 前端修改内容

建议修改：

- `src/types/mtm.ts`
- `src/utils/mtm.ts`
- `src/pages/MtmServiceCasesPage.vue`
- `src/pages/MtmServiceCaseDetailPage.vue`

### 6.2 列表页新增能力

列表页首版建议具备以下能力：

1. 识别 `preset_source`
2. 根据来源标识输出统一页面提示
3. 手动筛选时清除来源标识
4. 从详情返回时恢复来源标识

---

## 七、风险点

### 7.1 来源标识和筛选结果不再匹配

如果用户改了筛选，但来源标识还保留：

- 页面提示就会失真

因此首版必须在手动改筛选时清除该标识。

### 7.2 首页与列表页文案口径不一致

如果首页预设叫“当前阶段服务”，列表页却展示另一种说法：

- 用户会感觉像进了另一个场景

因此页面提示必须继续复用统一预设口径。

### 7.3 返回链路丢失来源标识

如果详情页不恢复来源标识：

- 用户返回列表后提示会消失

因此详情页返回构造函数必须同步扩展。

---

## 八、当前结论

`T-P0-18` 最合理的最小范围确定为：

- `MTM 列表页预设来源标识与页面提示统一`

推荐实现方向：

1. 不新增后端接口
2. 为首页预设入口新增单一正式来源标识
3. 列表页按来源标识展示统一提示
4. 用户手动改筛选时清除来源标识，避免误导
5. 以“用户一眼知道自己从哪里来、为什么看到当前结果”为本轮交付目标
