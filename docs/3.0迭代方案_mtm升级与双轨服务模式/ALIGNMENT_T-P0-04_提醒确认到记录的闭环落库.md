# ALIGNMENT_T-P0-04_提醒确认到记录的闭环落库

## 一、原始任务

任务来源：`TASK_P0_正式拆分.md` 中的 `T-P0-04 提醒确认到记录的闭环落库`

任务目标：

- 把提醒确认动作稳定映射为正式用药记录
- 形成“提醒 -> 确认 -> 记录 -> 统计”的完整链路

---

## 二、当前项目理解

### 2.1 已有前置能力

`T-P0-03` 已完成以下基础：

- 新增正式提醒确认接口 `POST /api/reminders/{id}/confirm/`
- 支持 `taken / missed / delayed / partial`
- 返回结构化 `record_payload`
- 已兼容提醒历史语义

### 2.2 当前阻塞点

当前 `MedicationRecord` 还不能直接承接提醒确认结果，主要原因有：

- `quantity_taken` 当前要求必须大于 0
- 但 `missed` 状态又要求数量应为 0
- 模型和序列化器对“漏服”语义存在直接冲突
- 当前记录模型没有 `reminder` 关联
- 当前记录模型没有 `scheduled_time`
- 当前库存扣减逻辑无法安全处理“重复确认 / 更新同一条提醒记录”

---

## 三、现有代码约束

### 3.1 记录模型的结构性问题

当前 `MedicationRecord` 字段适合手动录入，但不适合承接提醒闭环：

- 无法标记记录来自哪一条提醒
- 无法标记本次提醒原始计划时间
- 无法对同一提醒同一时段做幂等更新

### 3.2 库存扣减逻辑的风险

当前模型保存逻辑是：

- `taken / partial` 保存后直接扣库存
- 没有区分“首次创建”还是“后续更新”

这意味着：

- 如果同一条记录被更新，库存可能被重复扣减
- 如果需要补充提醒关联或修正状态，当前保存逻辑不安全

---

## 四、需求边界确认

### 4.1 本任务要做什么

本任务只负责：

- 让正式提醒确认接口能够创建或更新 `MedicationRecord`
- 为提醒来源记录建立可追踪字段
- 明确动作到记录状态的映射
- 明确库存扣减规则
- 明确去重 / 幂等策略

### 4.2 本任务不做什么

本任务不负责：

- 首页聚合
- 依从性统计最终聚合接口
- 提醒前端交互
- MTM 服务骨架

---

## 五、关键决策点与当前判断

### 5.1 是否修改 `MedicationRecord` 模型

当前判断：必须修改。

建议新增：

- `reminder`
- `scheduled_time`

原因：

- 没有关联字段就无法追踪提醒来源
- 没有计划时间就无法识别同一提醒的单次服药事件

### 5.2 漏服是否写入记录

当前判断：要写入。

原因：

- 否则提醒闭环无法形成完整统计
- 后续依从性分析需要识别真实漏服事件

前提：

- 放宽 `quantity_taken` 对 `missed` 的限制，允许为 0

### 5.3 延迟是否写入记录

当前判断：要写入。

策略：

- 记录状态记为 `delayed`
- 保留 `delay_minutes`
- `taken_at` 使用用户传入时间；若未传，则使用计划时间加延迟分钟数推导

这样后续才能统计延迟服药并保留时间差。

### 5.4 库存是否对延迟扣减

当前判断：应扣减。

原因：

- 在本轮语义中，`delayed` 表示“已晚服”，不是单纯“稍后提醒我”
- 如果不扣库存，会导致记录与库存不一致

### 5.5 幂等如何处理

当前判断：

- 不新建复杂去重表
- 通过 `user + reminder + scheduled_time` 进行 `update_or_create`

这样可保证：

- 同一提醒同一计划时间重复确认时，不会反复插入新记录
- 后续更改状态时可以更新同一条记录

---

## 六、建议实现方案

### 6.1 模型层

建议修改 `MedicationRecord`：

- `quantity_taken` 允许为 0
- 新增 `reminder` 外键
- 新增 `scheduled_time`
- 调整库存扣减逻辑，按“库存影响差值”更新，而不是每次保存都直接扣

### 6.2 提醒确认接口

在现有 `confirm` 接口中继续扩展：

- 基于 `record_payload` 同步正式记录
- 返回：
  - `record_id`
  - `record_created`
  - `record_payload`

### 6.3 记录映射规则

建议映射为：

- `taken -> status=taken, quantity_taken=提醒剂量`
- `missed -> status=missed, quantity_taken=0`
- `delayed -> status=delayed, quantity_taken=提醒剂量`
- `partial -> status=partial, quantity_taken=实际部分剂量`

---

## 七、风险点

- 如果只改接口不改模型，漏服场景仍然无法落库
- 如果只做创建不做更新，同一提醒重复确认会产生重复记录
- 如果不修库存扣减逻辑，后续任何更新操作都可能二次扣库存
- 如果延迟动作不统一定义，后面统计会混乱

---

## 八、当前结论

`T-P0-04` 需要同步改三层：

1. `MedicationRecord` 模型
2. 记录校验逻辑
3. 提醒确认接口中的正式落库逻辑

推荐实现方向：

1. 给 `MedicationRecord` 增加提醒来源追踪字段
2. 允许 `missed` 合法写入记录
3. 采用 `update_or_create` 做同一提醒同一计划时间的幂等更新
4. 把库存扣减改为“按差值修正”
5. 在 `confirm` 接口中返回正式记录信息
