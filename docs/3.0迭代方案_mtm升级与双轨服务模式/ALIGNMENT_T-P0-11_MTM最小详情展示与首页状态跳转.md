# ALIGNMENT_T-P0-11_MTM最小详情展示与首页状态跳转

## 一、原始任务

任务来源：

- 基于已完成的 `T-P0-10 MTM 最小入口与触发提示`

当前继续方向：

- 为首页最近服务状态补“进入详情”的最小闭环
- 让用户不仅能看到最近 MTM 服务状态，还能点进独立页面查看详情

---

## 二、当前项目理解

### 2.1 当前已具备的能力

当前项目已经具备：

- `apps.mtm` 最小模型骨架
- `GET /api/mtm/service-cases/`
- `POST /api/mtm/service-cases/`
- `GET /api/mtm/service-cases/{id}/`
- `POST /api/mtm/service-cases/{id}/transition/`
- 首页 `DashboardPage.vue` 中的 MTM 建议卡片
- 首页最近 3 条服务单状态展示

因此当前真正缺的，不是“再做一套 MTM 后端”，而是：

- 把首页最近状态从静态展示升级为可进入详情
- 给现有详情接口一个真实前端承接页面

### 2.2 为什么这是 `T-P0-11` 最合理的最小范围

`T-P0-10` 已经完成：

- 首页发起服务单
- 首页看到最近状态
- 未完成服务单防重复发起

如果下一步继续新增：

- 完整 MTM 列表页
- 问诊编辑页
- 评估编辑页
- 干预计划编辑页

会立刻把任务扩大成新的页面体系和工作台体系，不符合当前“P0 最小闭环”的节奏。

因此最顺的下一步是：

- 先把“状态可见”推进到“状态可点击查看”
- 先做一个最小详情页承接现有详情接口

### 2.3 当前项目的真实使用场景

当前项目仍以患者端视角为主，药师工作台和复杂协作未落地。

因此本轮详情页更适合定位为：

- 患者查看当前 MTM 服务进度
- 患者查看系统已沉淀的问诊、评估、计划、随访摘要

而不是：

- 药师操作台
- 多角色编辑入口

---

## 三、现有代码约束

### 3.1 后端能力约束

`T-P0-09` 的详情接口已经返回：

- 服务单主信息
- 问诊摘要
- 评估摘要
- 干预计划摘要
- 随访记录列表

因此本轮原则上不应新增新的后端详情接口或新的聚合接口，优先复用：

- `GET /api/mtm/service-cases/{id}/`

### 3.2 前端路由约束

当前前端路由集中在：

- `src/router/index.ts`

现有详情页模式已经存在：

- `/medicines/:id`
- `/reminders/:id`
- `/medical-records/:id`

因此本轮应沿用相同模式新增：

- `/mtm/service-cases/:id`

### 3.3 响应结构约束

当前项目前端 API 客户端会统一处理：

- `{ success, data, message }`

同时项目特别强调双层 `data` 嵌套要按真实结构解包。

因此本轮 MTM 详情页和详情 API 封装必须继续遵守：

- 不直接误用 `response.data.xxx`
- 按项目统一 `api` 封装后的结果读取真实 payload

### 3.4 页面风格约束

当前首页已重构为较新的卡片式任务风格，但其他详情页仍以“加载态 / 错误态 / 内容区”形式组织。

因此本轮详情页应做到：

- 结构清晰
- 可读性强
- 空态明确

但不必为了 MTM 单独造一套重型复杂工作台样式。

## 四、需求边界确认

### 4.1 本任务要做什么

本任务负责：

- 新增前端 MTM 服务单详情页
- 新增前端 MTM 详情 API 封装
- 补充 MTM 详情类型定义
- 新增前端路由
- 将首页最近服务状态改为可跳转到详情
- 在详情页展示最小详情内容和空态
- 补充关键日志
- 补充本轮对齐、共识、验收文档

### 4.2 本任务不做什么

本任务不负责：

- 新增后端接口
- 新增 MTM 列表页
- 首页之外的更多 MTM 入口
- 服务单状态流转按钮
- 问诊/评估/计划/随访编辑功能
- 药师工作台
- 药师分配逻辑

这些内容超出“最小详情展示与首页状态跳转”的范围。

---

## 五、关键歧义与当前判断

### 5.1 是否需要新增后端接口

当前判断：

- 不需要

原因：

- 现有 `GET /api/mtm/service-cases/{id}/` 已能承接首版详情展示
- 当前优先目标是复用既有后端成果，不重复扩接口

### 5.2 是否要先做 MTM 列表页

当前判断：

- 不做

原因：

- 首页已经能展示最近 3 条服务单
- 当前缺的不是“更多列表”，而是“能进入详情”

### 5.3 详情页需要支持状态流转吗

当前判断：

- 首版不支持

原因：

- 当前患者端为主，状态流转更接近后续专业操作
- 本轮目标是查看，不是编辑

### 5.4 首页从哪里进入详情

当前判断：

- 从“最近专业服务状态”区块进入
- 如果存在进行中服务，也应提供明显查看入口

原因：

- 这是 `T-P0-10` 已有展示区，改动最小
- 用户从刚创建成功后的状态区直接进入详情，路径最自然

### 5.5 详情页展示到什么粒度

当前判断：

- 只展示摘要，不做复杂编辑表单

建议最小展示内容：

- 服务编号
- 当前状态
- 触发来源
- 创建时间 / 启动时间 / 完成时间
- 服务目标
- 备注
- 患者基础信息
- 主责药师基础信息
- 问诊摘要块
- 评估摘要块
- 干预计划摘要块
- 随访记录列表

7. 支持手动刷新详情

## 七、风险点

### 7.1 误扩为完整 MTM 页面体系

如果本轮顺手新增：

- 列表页
- 编辑页
- 工作台

会直接破坏“最小闭环”节奏。

### 7.2 详情页字段直接堆 JSON

如果不做字段整理，直接把接口对象原样堆在页面上：

- 可读性会很差
- 不符合当前项目偏人话的展示风格

### 7.3 首页跳转链路不顺

如果只新增详情页但首页没有明显入口：

- 用户仍然只能看到状态，感知不到新闭环价值

---

## 八、当前结论

`T-P0-11` 最合理的最小范围确定为：

- `MTM 最小详情展示与首页状态跳转`

推荐实现方向：

1. 不新增后端接口
2. 复用 `/api/mtm/service-cases/{id}/`
3. 新增一个独立详情页
4. 在首页最近服务状态区接入详情跳转
5. 以“能进入、能查看、能看懂”为本轮交付目标
