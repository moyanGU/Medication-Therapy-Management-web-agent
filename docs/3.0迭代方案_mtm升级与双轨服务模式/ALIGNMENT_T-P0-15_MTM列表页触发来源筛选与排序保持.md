# ALIGNMENT_T-P0-15_MTM列表页触发来源筛选与排序保持

## 一、原始任务

任务来源：

- 基于已完成的 `T-P0-14 MTM 列表页与详情页之间的筛选联动 / 路由查询保持`

当前继续方向：

- 为 MTM 列表页补“触发来源筛选”
- 为 MTM 列表页补“排序方式”
- 把这两个新状态也纳入 URL 联动与详情返回上下文

---

## 二、当前项目理解

### 2.1 当前已具备的能力

当前项目已经具备：

- MTM 独立列表页
- 搜索、状态筛选、分页
- `page` / `search` / `status` 的 URL 保持
- 从列表进入详情再返回时恢复上下文
- 后端列表接口已支持 `trigger_source` 与 `ordering`

因此当前真正缺的，不是新的接口，而是：

- 把后端已具备但前端未开放的筛选和排序能力补出来
- 并继续保持和 `T-P0-14` 一致的 URL 联动能力

### 2.2 为什么这是 `T-P0-15` 最合理的最小范围

当前列表页已经解决了：

- 搜索保持
- 状态筛选保持
- 页码保持
- 返回上下文保持

下一个最自然的增量，不是再做新页面，而是：

- 把最有价值的两个列表能力继续接上

如果下一步直接做：

- 更多高级筛选
- 多字段组合排序
- 批量操作

会把任务快速扩大成后台级列表器。

因此当前最合理的最小范围是：

- 只新增 `trigger_source` 筛选
- 只新增最小排序选择
- 并把这两个状态继续纳入 URL 查询保持

### 2.3 当前项目的真实使用场景

当前项目仍以患者端浏览为主。

因此本轮排序和筛选更适合用于：

- 更快找到自己想看的服务单
- 区分是主动申请、依从性预警还是复诊到期触发的服务
- 选择最近创建或最早创建等简单排序方式

而不是：

- 专业后台数据分析面板
- 药师工作队列管理

## 三、现有代码约束

### 3.1 后端接口约束

当前后端列表接口已支持：

- `trigger_source`
- `ordering`

其中排序字段明确为：

- `created_at`
- `started_at`
- `completed_at`

因此本轮前端必须严格只暴露后端已允许的排序值，不应自创字段。

### 3.2 当前列表页状态约束

当前列表页已经把以下内容写入 URL：

- `page`
- `search`
- `status`

但尚未覆盖：

- `trigger_source`
- `ordering`

因此本轮要做的是：

- 在现有 URL 联动方案上继续扩展
- 不要另起一套新的状态保持方式

### 3.3 当前详情页返回约束

当前详情页已经可以恢复：

- `page`
- `search`
- `status`

因此本轮应继续扩展为：

- `page`
- `search`
- `status`
- `trigger_source`
- `ordering`

而不是重写详情页整体返回逻辑。

### 3.4 页面复杂度约束

当前列表页已经有搜索和状态筛选区。

因此本轮更适合：

- 在同一区块补两个新增控件

而不是：

- 增加新的高级筛选折叠面板
- 增加单独工具栏页签

## 四、需求边界确认

### 4.1 本任务要做什么

本任务负责：

- 在 MTM 列表页新增触发来源筛选
- 在 MTM 列表页新增排序选择
- 将 `trigger_source` 与 `ordering` 同步到路由查询参数
- 刷新后按查询参数恢复这两个状态
- 从列表进入详情时保留这两个上下文
- 详情页返回时恢复这两个上下文
- 补充本轮对齐、共识、验收文档

### 4.2 本任务不做什么

本任务不负责：

- 新增后端接口
- 新增更多高级筛选
- 新增多字段组合排序
- 新增默认排序规则变更
- 重构列表页布局
- 重构详情页主体内容

这些内容超出“触发来源筛选与排序保持”的范围。

## 五、关键歧义与当前判断

### 5.1 触发来源要暴露哪些值

当前判断：

- 直接暴露已存在的全部最小触发来源：
  - `manual`
  - `self_requested`
  - `adherence_alert`
  - `followup_due`
  - `polypharmacy`
  - `referral`

原因：

- 都已在现有类型和文案映射中定义
- 无需新增额外业务解释成本

### 5.2 排序要暴露哪些选项

当前判断：

- 首版只暴露最容易理解的几种：
  - 最新创建优先 `-created_at`
  - 最早创建优先 `created_at`
  - 最近启动优先 `-started_at`
  - 最近完成优先 `-completed_at`

原因：

- 都与后端允许字段一致
- 能覆盖用户最常见的查看需求

### 5.3 排序是否算“筛选条件”

当前判断：

- 排序属于列表显示方式，不算空态里的“筛选条件”

原因：

- 仅排序变化不应导致空态提示文案变成“筛选后为空”

### 5.4 查询参数是否继续用 `replace`

当前判断：

- 继续优先使用 `router.replace`

原因：

- 和 `T-P0-14` 保持一致
- 避免切换排序和筛选造成过多历史记录

5. 进入详情后返回时恢复

## 七、风险点

### 7.1 前端排序值与后端排序字段不一致

如果前端写了后端不支持的排序值：

- 会导致接口无效或返回错误

因此排序选项必须严格基于后端 `ordering_fields`。

### 7.2 查询参数越来越多后比较逻辑失准

如果只新增字段但不统一扩展标准化函数：

- 可能出现 URL 已更新但页面判断未更新

因此必须同步更新：

- 查询参数解析函数
- 查询参数标准化函数
- 详情页返回参数构造函数

### 7.3 返回上下文只恢复部分字段

如果详情页只恢复旧字段，不恢复新增字段：

- 用户会感知为“返回后排序变了”或“筛选丢了”

因此本轮必须把新增的两个字段也纳入返回上下文。

---

## 八、当前结论

`T-P0-15` 最合理的最小范围确定为：

- `MTM 列表页触发来源筛选与排序保持`

推荐实现方向：

1. 不新增后端接口
2. 复用现有 `trigger_source` 和 `ordering` 能力
3. 在列表页补两个最小新增控件
4. 将两个字段纳入 URL 查询和详情返回上下文
5. 以“更容易筛选、更容易排序、刷新和返回都不丢状态”为本轮交付目标
