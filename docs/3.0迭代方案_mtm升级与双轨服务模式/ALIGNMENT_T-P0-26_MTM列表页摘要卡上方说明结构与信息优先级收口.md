# ALIGNMENT_T-P0-26_MTM列表页摘要卡上方说明结构与信息优先级收口

## 一、原始任务

任务来源：

- 基于已完成的 `T-P0-25 MTM 列表页分页状态与结果说明层级收口`

当前继续方向：

- 让摘要卡上方说明不再一层层堆叠
- 让“来源说明 / 当前条件”按优先级只显示最关键的信息

---

## 二、当前项目理解

### 2.1 当前已具备的能力

当前列表页摘要卡已经具备：

- 结果摘要 `listDescription`
- 来源说明 `presetSourceTitle + presetSourceDescription`
- 条件说明 `activeFilterSummaryText`
- 推荐下一步 `recommendedAction.description`
- 补充动作 `summaryActions`

因此当前还残留的体验问题是：

- 摘要卡上方说明行数偏多
- 来源说明和当前条件容易连续堆叠
- 用户进入页面后，不容易第一眼判断“当前最该看哪条说明”

这会导致：

- 摘要卡信息层级不够清晰
- 上半区文字密度偏高
- 与前几轮“单一路径收口”的方向还差最后一小步

### 2.2 为什么这是 `T-P0-26` 最合理的最小范围

`T-P0-25` 已经把结果区页码状态收口到了唯一展示位。

当前继续做最自然的一步，不是继续改分页或按钮，而是把摘要卡主体里的说明结构再收一层：

- 哪条是主结果说明
- 哪条是上下文说明
- 哪条是下一步提示

因此本轮最合理的最小范围是：

- 只处理摘要卡上方说明结构
- 只调整说明信息的展示优先级
- 不改变动作、结果、分页和列表行为

### 2.3 当前项目的真实使用场景

当前 MTM 列表页仍以患者端轻量浏览为主，因此本轮更适合：

- 降低摘要卡文字堆叠感
- 强化“结果摘要 -> 当前上下文 -> 推荐下一步”的阅读顺序

而不是：

- 新增新的文案场景体系
- 改造按钮系统
- 扩展筛选或列表能力

## 三、现有代码约束

### 3.1 当前模板约束

当前 `MtmServiceCasesPage.vue` 摘要卡上方的说明区包含多个独立段落：

1. `listDescription`
2. `presetSourceTitle + presetSourceDescription`
3. `activeFilterSummaryText`
4. `recommendedAction.description`

最小改法应是：

- 保留这些信息来源
- 改成按场景优先级派生
- 避免同一区域重复解释当前上下文

### 3.2 当前状态约束

本轮必须继续复用现有状态：

- `presetSource`
- `presetSourceTitle`
- `presetSourceDescription`
- `activeFilterSummaryText`
- `recommendedAction`
- `hasManualAdjustments`

也就是说，本轮可以改的是：

- 上下文说明的展示顺序
- 是否隐藏次要说明
- 是否把说明统一收口到 `computed`

不应改动：

- 动作规则
- 查询参数同步
- 接口请求
- 列表和分页行为

### 3.3 当前范围约束

根据当前阶段目标，本轮必须严格保持：

- 只改 `src/pages/MtmServiceCasesPage.vue`
- 不改接口
- 不改路由
- 不改 `src/utils/mtm.ts`
- 不改首页、详情页、空态、底部分页条和列表项卡片

## 四、需求边界确认

### 4.1 本任务要做什么

本任务负责：

- 收口摘要卡上方说明结构
- 让摘要卡只显示当前最关键的上下文说明
- 保持“结果摘要 -> 上下文 -> 推荐下一步”的层级顺序
- 补充本轮对齐、共识、验收文档

### 4.2 本任务不做什么

本任务不负责：

- 修改快捷动作和推荐动作逻辑
- 修改页码状态和底部分页条
- 修改列表项卡片内容
- 修改接口、路由和 query 参数
- 新增新的筛选或结果区能力

---

## 五、关键歧义与当前判断

### 5.1 来源说明和当前条件是否都要同时显示

当前判断：

- 不强制同时显示

原因：

- 本轮目标是层级收口，不是信息堆叠
- 同一区域应优先显示最关键的一条上下文说明

### 5.2 哪类信息优先级更高

当前判断：

- 首页预设来源说明优先于手动条件说明

原因：

- 预设来源代表当前页面入口语义
- 手动条件说明更适合在无预设来源时承接上下文

### 5.3 推荐下一步是否继续保留

当前判断：

- 保留

原因：

- 它承接的是“下一步该怎么做”
- 与“当前上下文说明”职责不同

---

## 六、建议实现边界

### 6.1 前端修改内容

建议只修改：

- `src/pages/MtmServiceCasesPage.vue`

### 6.2 建议最小实现方式

建议新增一个摘要卡上下文说明 `computed`，统一输出：

1. 标签
2. 描述

建议优先级为：

1. 首页预设来源说明
2. 手动条件说明
3. 默认场景不额外显示上下文说明

### 6.3 建议交付表现

本轮页面首版建议具备：

1. 摘要卡上方说明行数减少
2. 信息层级更容易一眼看懂
3. 推荐下一步仍然可见，但不和上下文说明混在一起

---

## 七、风险点

### 7.1 收口过度导致信息丢失

如果直接删掉过多说明：

- 用户可能不清楚自己为什么看到当前结果

因此本轮应保留“最关键的一条上下文说明”，而不是全部移除。

### 7.2 再造一套新文案体系

如果为本轮再单独造一套复杂说明规则：

- 会增加维护成本

因此本轮只基于现有状态做最小优先级派生。

### 7.3 推荐说明和上下文说明再次混层

如果把推荐动作说明也并入上下文说明：

- 会破坏前几轮建立的主路径层级

因此本轮继续分开“当前是什么”和“下一步做什么”。

---

## 八、当前结论

`T-P0-26` 最合理的最小范围确定为：

- `MTM 列表页摘要卡上方说明结构与信息优先级收口`

推荐实现方向：

1. 不改动作规则和分页状态
2. 不改接口、路由和工具函数
3. 仅在 `MtmServiceCasesPage.vue` 中收口摘要卡上方说明优先级
4. 让摘要卡形成“结果摘要 -> 当前上下文 -> 推荐下一步”的清晰阅读顺序
