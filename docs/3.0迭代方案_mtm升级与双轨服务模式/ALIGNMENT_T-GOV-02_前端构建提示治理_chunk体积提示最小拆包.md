当前继续方向：

- 优先用最小打包策略收口，而不是改业务代码或大量重构导入方式

## 二、当前项目理解

### 2.1 当前构建提示现状

最新构建中仍保留的主要 warning：

1. `sonner` 的 `"use client"` bundling 提示
2. `@page-agent/page-controller` 的 `eval` 警告
3. chunk 体积提示

当前最适合作为第二刀治理的是：

- chunk 体积提示

原因：

1. 相比三方库 warning，更容易在本项目构建配置层收口
2. 有机会带来实际构建结果改善，而不只是压日志
3. 不需要先触碰三方库内部行为

### 2.2 当前重依赖分布

当前已确认：

1. 路由层本身已经大量使用动态导入
2. `@page-agent/core` 与 `@page-agent/page-controller` 主要集中在 `src/services/pageAgentService.ts`
3. `jspdf` 与 `html2canvas` 主要集中在 `src/utils/pdfExport.ts`
4. `sonner / vue-sonner` 只在少量页面和表单中使用

这说明当前 chunk 偏大的原因，不是“完全没有拆路由”，而是：

- 某些三方依赖仍被打进较重 chunk
- 现有默认拆包策略对这些库的隔离不够

### 2.3 为什么不先处理 `sonner` / `page-agent` warning

当前不优先直接处理：

- `sonner` 的 `"use client"` 提示
- `@page-agent/page-controller` 的 `eval` 警告

原因：

1. 这两条更多是三方包实现层行为
2. 直接治理可能涉及依赖升级、替换或更大范围兼容验证
3. 当前工程治理仍应优先选择“本项目可控”的切口

因此本轮最合理的最小范围是：

- 只在 `vite.config.ts` 里增加最小 `manualChunks` 策略
- 先隔离最明显的重依赖组

## 七、风险点

### 7.1 拆包过度

如果一次拆得太细：

- 会增加调试和缓存复杂度

因此本轮只按少量依赖组拆包。

### 7.2 拆包无效

如果当前 warning 主要来自业务代码本身：

- 仅靠 `manualChunks` 可能改善有限

因此本轮需要用构建结果验证，而不是预设成功。

### 7.3 混入其他 warning 治理

如果顺手继续处理三方包 warning：

- 会导致本轮范围扩大

因此本轮只看 chunk 体积提示。
