# ALIGNMENT_T-P0-12_MTM详情页最小状态推进

## 一、原始任务

任务来源：

- 基于已完成的 `T-P0-11 MTM 最小详情展示与首页状态跳转`

当前继续方向：

- 为已有 MTM 详情页补上最小状态推进能力
- 让系统中的服务单不仅“可创建、可查看”，也能在前端被最小推进

---

## 二、当前项目理解

### 2.1 当前已具备的能力

当前项目已经具备：

- `POST /api/mtm/service-cases/`
- `GET /api/mtm/service-cases/`
- `GET /api/mtm/service-cases/{id}/`
- `POST /api/mtm/service-cases/{id}/transition/`
- 首页发起 MTM 服务单
- 首页查看最近服务状态
- 首页进入 MTM 详情页
- 详情页查看主信息与关联摘要

因此当前真正缺的，不是新的后端主线，而是：

- 前端没有入口去调用 `transition`
- 已有状态机虽然落地，但用户侧无法最小演示和验证它

### 2.2 为什么这比先做独立列表页更合理

当前链路已经是：

- 首页发起
- 首页看状态
- 详情页看详情

如果下一步先做列表页：

- 会新增“查看更多”，但不会带来新的流程推进能力
- 状态机仍然只存在于后端测试和 API 层

而如果先做详情页最小推进：

- 可以直接复用现有 `transition` 接口
- 可以把“状态能追踪”推进到“状态能前端驱动验证”
- 更符合“先打通闭环，再做高级体验”

### 2.3 当前项目的真实使用场景

当前项目仍然缺少正式药师角色与药师工作台。

因此本轮更适合采用：

- 前端最小演示式推进
- 聚焦流程验证

而不是：

- 复杂审批流
- 角色化流转控制
- 多人协作状态编辑

---

## 三、现有代码约束

### 3.1 后端状态机约束

当前模型和接口已经固定最小合法流转：

- `pending -> interviewing`
- `interviewing -> assessing`
- `assessing -> intervening`
- `intervening -> following_up`
- `intervening -> completed`
- `following_up -> completed`

因此本轮前端必须：

- 完整尊重后端既有状态机
- 不能自己发明新的状态
- 不能允许任意跳转

### 3.2 页面承接约束

当前 `MtmServiceCaseDetailPage.vue` 已经具备：

- 服务单主信息展示
- 摘要区块展示
- 刷新详情

因此本轮最合适的承接位置就是：

- 详情页顶部或概览区域

而不是再新开一个独立“状态管理页”。

### 3.3 交互复杂度约束

当前 `transition` 接口只要求：

- `target_status`

可选：

- `notes`

因此本轮最小前端实现不必引入复杂表单，建议：

- 直接展示“下一步操作”按钮
- 自动带最小备注，或允许不传备注

### 3.4 响应结构约束

当前项目前端必须继续正确处理：

- `{ success, data, message }`
- 双层 `data` 解包规则

因此本轮 transition API 封装必须继续复用现有 `api` 工具，不要手写 fetch。

## 四、需求边界确认

### 4.1 本任务要做什么

本任务负责：

- 为 MTM 详情页增加最小状态推进能力
- 前端补充 transition API 封装
- 前端补充可选的状态推进类型定义
- 在详情页展示当前可执行的下一步动作
- 状态推进成功后刷新详情并提示结果
- 补充本轮对齐、共识、验收文档

### 4.2 本任务不做什么

本任务不负责：

- 修改后端状态机规则
- 增加新状态
- 增加角色权限体系
- 增加审批流
- 增加独立 MTM 列表页
- 增加问诊/评估/计划/随访编辑
- 增加复杂备注输入弹窗

这些内容超出“最小状态推进”的范围。

---

## 五、关键歧义与当前判断

### 5.1 谁可以推动状态

当前判断：

- 首版沿用后端现有参与者权限

原因：

- 当前后端已经允许参与者范围访问并执行接口
- 现阶段没有正式药师角色体系，前端不应提前做一套新权限判断

### 5.2 是不是要支持所有跳转

当前判断：

- 不支持自由选择所有状态
- 仅展示当前状态下的合法后续状态

原因：

- 必须与后端状态机一致
- 避免前端把流程语义弄脏

### 5.3 是否需要备注输入框

当前判断：

- 首版不做单独输入框

建议：

- 自动生成最小备注

原因：

- 可以减少交互复杂度
- 足以完成最小闭环验证

### 5.4 `intervening` 的双分支怎么处理

当前判断：

- 显示两个按钮
- 分别对应：
  - 进入随访
  - 直接完成

原因：

- 后端已允许两条分支
- 首版只要清晰展示即可，不必加弹窗分流

## 六、建议实现边界

### 6.1 前端新增/修改内容

建议修改：

- `src/api/mtm.ts`
- `src/types/mtm.ts`
- `src/utils/mtm.ts`
- `src/pages/MtmServiceCaseDetailPage.vue`

### 6.2 详情页新增能力

详情页首版建议具备以下状态推进能力：

1. 展示当前状态
2. 展示当前可推进的后续动作
3. 点击后调用 transition 接口
4. 按钮提交中禁用重复点击
5. 成功后刷新详情
6. 成功后显示 toast
7. 非法状态或接口失败时显示明确错误

---

## 七、风险点

### 7.1 前端规则与后端规则不一致

如果前端自己写错了可推进状态：

- 会造成按钮显示错误
- 也会给用户造成误导

因此前端规则必须严格映射后端当前状态机。

### 7.2 交互做得过重

如果本轮引入：

- 表单弹窗
- 审批确认
- 多层说明

会让任务范围失控。

### 7.3 推进后页面不刷新

如果状态推进成功但页面仍显示旧状态：

- 用户会误以为操作失败

因此成功后必须立即刷新详情。

---

## 八、当前结论

`T-P0-12` 最合理的最小范围确定为：

- `MTM 详情页最小状态推进`

推荐实现方向：

1. 不修改后端状态机
2. 复用 `/api/mtm/service-cases/{id}/transition/`
3. 在详情页展示合法下一步动作
4. 成功后刷新详情并更新当前状态
5. 以“能推进、能反馈、能继续查看”为本轮交付目标
