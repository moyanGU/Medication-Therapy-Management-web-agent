# MTM-Helper 3.0 实施重排建议

## 一、这份文档解决什么问题

原始《迭代方案_mtm升级与双轨服务模式.md》适合作为方向文档，但以当前项目现状来看，内容跨度过大，不能直接作为逐项排期和开发清单。

本文件的目标是：

- 按当前仓库真实能力重排实现顺序
- 区分“可立即开工”和“需要后置建设”的内容
- 避免一开始同时推进链路A、链路B、AI增强、生态集成，导致系统复杂度失控
- 给出适合当前项目的最小落地路径

---

## 二、当前项目基线判断

### 2.1 已有基础

当前主项目已经具备以下正式能力：

- 用户认证与基础用户体系
- 药品管理
- 用药提醒
- 用药记录
- 用药计划
- 就医记录
- 审计日志
- 部分敏感字段加密
- 保守型 Page Agent 页面辅助

这意味着当前系统已经具备较完整的“链路A：日常家居用药管理”底座。

### 2.2 当前缺口

当前系统尚未真正落地以下“链路B：专业MTM服务”核心能力：

- 独立的 MTM 服务主实体
- 六步服务流程状态机
- 药学问诊模块
- SOAP 药历模块
- PMR / MAP 模块
- 药师工作台
- 五维评估引擎
- 患者 / 药师 / 医生 / 家属的协作角色模型
- 基于授权关系的专业访问控制

### 2.3 结论

当前项目不是“从零做 MTM”，而是：

- 链路A已经有产品形态
- 链路B还没有业务骨架
- AI能力已经接入，但只能做辅助，不能直接承担专业 MTM 核心决策

因此后续建设必须遵循：

1. 先做链路A闭环增强
2. 再做链路B最小闭环骨架
3. 最后再做 AI 增强与生态扩展

---

## 三、重排原则

### 3.1 原则一：先补现有闭环，再开新业务域

已有提醒、记录、计划、就医记录都能继续增量演进，应优先做高收益补强，不要过早切入大型新模块。

### 3.2 原则二：链路B先做“最小专业闭环”

链路B不应一开始就追求“完整 MTM 平台”，而应先完成一个能跑通的最小专业服务闭环：

- 服务启动
- 问诊采集
- 评估记录
- 干预计划
- 随访记录

### 3.3 原则三：AI只能后置增强

AI 辅助评估、SOAP 自动生成、干预建议生成，必须建立在结构化数据模型稳定之后，否则只能停留在文本生成层，无法真正进入业务闭环。

### 3.4 原则四：优先单体演进，避免过早拆服务

当前主项目以 Django + DRF 为中心，短期内应尽量继续在现有单体中扩展，不建议立刻引入：

- GraphQL
- FastAPI 独立服务
- Neo4j
- TensorFlow / PyTorch 服务
- Elasticsearch
- InfluxDB
- ClickHouse

这些技术在后续有价值，但不应成为当前阶段的先决条件。

---

## 四、建议重排后的实施范围

## 4.1 P0：立即开工项

这部分直接建立在当前代码基础上，风险最低，收益最高。

### P0-A1 智能首页重构

目标：

- 把当前通用仪表板升级为“今日任务 + 健康概览 + 风险提醒 + 快捷操作”的动态首页
- 首页优先服务链路A用户

建议内容：

- 展示今日待服药事项
- 展示漏服和延迟情况
- 展示低库存和临期药品
- 展示最近就医和复诊提醒
- 预留“需要专业用药指导？”入口

验收标准：

- 用户登录后首页信息基于真实数据生成
- 首页不再只是功能导航，而是任务型首页

### P0-A2 服药确认闭环

目标：

- 把“提醒 -> 记录”补成完整闭环

建议内容：

- 在提醒详情和提醒消息入口增加一键确认服药
- 自动生成来源为提醒的用药记录
- 支持漏服、延迟服用、部分服用
- 与依从性统计联动

验收标准：

- 用户可直接从提醒触发确认服药
- 确认结果能进入记录和统计
- 延迟与漏服可独立统计

### P0-A3 依从性评分与展示

目标：

- 让现有记录和提醒数据真正产生“用药依从性反馈”

建议内容：

- 按日、周、月生成依从性分数
- 在首页和统计页显示趋势
- 对连续低依从性用户触发风险提醒

验收标准：

- 至少支持最近 7 天和最近 30 天依从性统计
- 评分与真实记录联动，不使用模拟数据

### P0-A4 链路B最小数据骨架设计与落库

目标：

- 为专业 MTM 服务建立真正的后端主线

必须新建的最小实体建议：

- `MTMServiceCase`
  - 服务编号
  - 患者
  - 主责药师
  - 服务状态
  - 触发来源
  - 启动时间
  - 完成时间
- `MTMInterview`
  - 基本信息快照
  - 用药史
  - 过敏史
  - 生活方式
  - 经济情况
  - 健康期望
- `MTMAssessment`
  - 适宜性
  - 有效性
  - 安全性
  - 依从性
  - 经济性
  - 问题清单
- `MTMPlan`
  - 干预措施
  - 优先级
  - 患者确认状态
- `MTMFollowUp`
  - 随访时间
  - 随访方式
  - 执行情况
  - 风险变化
  - 下次随访计划

验收标准：

- 后端完成模型、迁移、基础 CRUD
- 状态流转至少支持：待开始 / 问诊中 / 评估中 / 干预中 / 随访中 / 已完成
- 不强行接入 AI

### P0-A5 链路B最小入口

目标：

- 让专业服务从“文档概念”变成系统中的真实入口

建议内容：

- 首页增加专业指导入口
- 满足基础条件时给出“建议进入专业服务”提示
- 先支持手动发起和规则提示发起

首版触发条件建议保守化：

- 用药数达到阈值
- 存在多个慢病记录
- 连续依从性较低
- 用户主动申请

验收标准：

- 用户可以创建第一条 MTM 服务单
- 系统里能看到服务状态变化

## 4.2 P1：第二阶段建设项

这部分应建立在 P0 完成之后推进。

### P1-B1 药学问诊表单

目标：

- 对照行动指南，把链路B“信息收集”结构化

建议内容：

- 分步骤表单
- 草稿保存
- 恢复编辑
- 关键字段完整性检查

### P1-B2 SOAP 基础版

目标：

- 先支持人工填写与归档，不追求 AI 自动生成

建议内容：

- S / O / A / P 四段结构化编辑
- 与 MTM 服务单关联
- 支持历史版本查看

### P1-B3 PMR / MAP 基础版

目标：

- 建立可交付给患者的专业产物

建议内容：

- PMR：个人用药记录
- MAP：面向患者的行动计划
- 支持基础打印或 PDF 导出

### P1-B4 药师工作台基础版

目标：

- 从“患者自助工具”过渡到“患者 + 药师协同系统”

建议内容：

- 待处理服务单
- 服务状态筛选
- 患者用药信息聚合查看
- 快速进入问诊、评估、计划、随访

### P1-B5 专业角色与授权关系

目标：

- 支撑后续专业协作，而不是继续沿用单一用户权限模型

建议内容：

- 新增药师角色
- 预留医生查看角色
- 预留家属受托查看关系
- 引入患者授权确认

## 4.3 暂缓项

以下内容不是没有价值，而是不适合当前立即推进。

### 暂缓-C1 AI 深度评估

包括：

- AI 预识别药物治疗问题
- AI 自动生成干预建议
- SOAP 自动书写
- 随访自动总结

暂缓原因：

- 当前没有稳定的结构化 MTM 数据输入
- 先做只会生成“看起来很专业”的文本，无法进入真实业务闭环

### 暂缓-C2 大规模技术扩容

包括：

- GraphQL
- FastAPI 独立服务
- 知识图谱
- 机器学习服务
- 全文检索
- 时序数据库

暂缓原因：

- 当前最大问题不是性能和扩展性，而是专业业务域尚未成型

### 暂缓-C3 生态集成

包括：

- HIS 对接
- 药店系统对接
- 医保系统对接
- 第三方健康 App 同步

暂缓原因：

- 自身业务闭环尚未跑通，对外集成会大幅放大复杂度

### 暂缓-C4 高阶合规承诺

包括：

- 完整 MFA
- 合规认证申报
- 联邦学习 / 差分隐私
- 全流程删除与数据便携权交付

暂缓原因：

- 当前更适合先补齐授权、审计、导出确认、敏感字段治理等“可直接落地”的合规基础

---

## 五、推荐实施顺序

### 第一批：链路A快速增益

建议顺序：

1. 智能首页重构
2. 服药确认闭环
3. 依从性评分与展示

原因：

- 直接服务现有主用户
- 复用现有模型最多
- 成果可见、风险低

### 第二批：链路B最小骨架

建议顺序：

1. MTM 服务主实体
2. 服务状态机
3. 创建入口
4. 基础问诊结构

原因：

- 没有主实体就无法承接专业流程
- 没有状态机就无法形成真实工作流

### 第三批：专业文档与工作台

建议顺序：

1. SOAP 基础版
2. PMR / MAP 基础版
3. 药师工作台基础版

原因：

- 这部分是真正让链路B从“流程”变成“服务产品”的关键

### 第四批：AI 增强

建议顺序：

1. AI 问诊辅助
2. AI SOAP 草稿辅助
3. AI 干预建议辅助
4. AI 随访总结辅助

原因：

- 只能建立在前面三个批次稳定之后

## 六、建议拆成的实际开发阶段

## 阶段 S1：链路A增强

范围：

- 智能首页
- 服药确认闭环
- 依从性展示

目标：

- 让当前产品从“功能集合”升级为“任务驱动型用药助手”

## 阶段 S2：链路B骨架

范围：

- MTM 服务单
- 问诊数据结构
- 评估数据结构
- 干预计划
- 随访记录

目标：

- 在系统中跑通第一条专业 MTM 服务链路

## 阶段 S3：专业交付物

范围：

- SOAP
- PMR
- MAP
- 药师工作台

目标：

- 让专业服务具备真实交付形态

## 阶段 S4：AI 辅助增强

范围：

- 问诊辅助
- 评估辅助
- 文档辅助
- 随访辅助

目标：

- 提升专业人员效率，不替代人工专业判断

---

## 七、不建议现在就做的事情

- 不建议现在同时重构前后端所有模块
- 不建议现在引入多个新基础设施
- 不建议现在就承诺完整医疗级智能评估
- 不建议现在把 Page Agent 当成专业 MTM 决策核心
- 不建议现在把链路B做成覆盖所有角色和所有场景的超大系统

---

## 八、最小可执行版本定义

如果当前只允许启动一轮有限开发，建议把目标收缩为：

### MVP-1

- 智能首页
- 服药确认闭环
- 依从性评分展示

### MVP-2

- MTM 服务单模型
- 手动发起专业服务
- 基础问诊表
- 评估问题清单
- 干预计划记录
- 随访记录

### MVP-3

- SOAP 基础版
- PMR / MAP 基础导出
- 药师待办工作台

---

## 九、最终结论

基于当前项目现状，原始 3.0 方案应做如下理解：

- 可以继续推进
- 但必须重排
- 不能“全量并行”
- 不能“先做 AI 再补业务”
- 不能“先铺大架构再补核心流程”

最稳妥、最适合当前项目的路径是：

1. 先把链路A做深
2. 再把链路B做成最小专业闭环
3. 然后再做 AI 辅助增强

如果后续正式进入开发，本文件可直接作为下一轮任务拆分的输入基础。
