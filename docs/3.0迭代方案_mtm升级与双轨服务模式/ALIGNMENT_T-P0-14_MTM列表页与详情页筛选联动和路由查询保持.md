# ALIGNMENT_T-P0-14_MTM列表页与详情页筛选联动和路由查询保持

## 一、原始任务

任务来源：

- 基于已完成的 `T-P0-13 MTM 独立列表页与历史服务承接`

当前继续方向：

- 让 MTM 列表页的搜索、状态筛选、页码可以写进 URL
- 让用户从列表进入详情后，返回时还能回到原来的筛选结果和页码

---

## 二、当前项目理解

### 2.1 当前已具备的能力

当前项目已经具备：

- `MTMServiceCasesPage.vue` 独立列表页
- 列表页搜索、状态筛选、分页
- `MtmServiceCaseDetailPage.vue` 详情页
- 从列表页进入详情页
- 首页进入列表页和详情页

因此当前真正缺的，不是新的业务能力，而是：

- 列表页状态的可分享、可刷新保持
- 列表页与详情页之间的上下文回跳能力

### 2.2 为什么这是 `T-P0-14` 最合理的最小范围

当前链路已经做到：

- 首页查看全部
- 列表浏览
- 进入详情

但仍有明显体验断点：

- 列表页一刷新，搜索词、状态筛选和页码会丢
- 进入详情后点击返回，拿不到列表上下文

如果现在直接做：

- 触发来源筛选
- 高级排序
- 多条件联动

会继续扩展列表页能力，却没有先修掉最基础的“上下文丢失”问题。

因此当前最合理的最小范围是：

- 先把列表上下文固化到路由查询参数
- 再把详情页返回动作接回带查询参数的列表页

### 2.3 当前项目的真实使用场景

当前项目更偏患者端自助浏览。

因此本轮更适合定位为：

- 保持用户浏览上下文
- 让历史服务查看更顺手

而不是：

- 新增复杂工作台导航
- 新增后台级列表控制器

---

## 三、现有代码约束

### 3.1 当前列表页状态约束

当前 `MtmServiceCasesPage.vue` 中：

- 搜索词保存在 `searchInput`
- 状态筛选保存在 `filters.status`
- 页码保存在 `page`

这些状态只存在于页面内存中，没有同步到 `route.query`。

因此当前一旦：

- 页面刷新
- 复制链接分享
- 从详情返回

原始列表上下文就会丢失。

### 3.2 当前详情页返回约束

当前 `MtmServiceCaseDetailPage.vue` 的返回逻辑是：

- 有历史记录就 `router.back()`
- 否则回首页

这意味着：

- 从列表页进入详情时，返回结果依赖浏览器历史
- 一旦刷新详情页或新开标签页，返回就无法回到带筛选条件的列表页

### 3.3 路由查询模式约束

当前项目里已有读取 `route.query` 的实现模式，如：

- `MedicinesPage.vue`
- `MedicalRecordForm.vue`

因此本轮应复用现有项目风格：

- 读取 `route.query`
- 解析为本地状态
- 再把本地状态回写到 `router.replace` 或 `router.push`

### 3.4 响应结构约束

本轮只是路由与前端状态联动，不新增后端接口。

因此仍然继续复用：

- `GET /api/mtm/service-cases/`
- `GET /api/mtm/service-cases/{id}/`

## 四、需求边界确认

### 4.1 本任务要做什么

本任务负责：

- 将 MTM 列表页的搜索、状态、页码同步到路由查询参数
- 页面刷新后按查询参数还原列表状态
- 浏览器前进后退时保持列表状态联动
- 从列表进入详情时带上最小返回上下文
- 详情页返回时优先回到带筛选条件的列表页
- 补充本轮对齐、共识、验收文档

### 4.2 本任务不做什么

本任务不负责：

- 新增后端接口
- 新增触发来源筛选
- 新增高级排序
- 新增更多筛选字段
- 重构详情页主体内容
- 重构首页结构

这些内容超出“筛选联动与路由查询保持”的范围。

---

## 五、关键歧义与当前判断

### 5.1 要保留哪些查询参数

当前判断：

- 首版只保留：
  - `page`
  - `search`
  - `status`

原因：

- 这正好覆盖当前列表页已存在的核心状态
- 不需要为未来未开放的筛选字段提前加复杂约定

### 5.2 列表页状态变更时用 `push` 还是 `replace`

当前判断：

- 优先使用 `router.replace`

原因：

- 避免用户每次输入搜索词、切换筛选都堆积大量历史记录
- 本轮重点是“保持状态”，不是“记录每次筛选操作历史”

### 5.3 详情页返回优先级怎么定

当前判断：

- 如果详情页 query 中存在来自列表页的上下文，就优先回列表页
- 否则保持原有回退逻辑

原因：

- 兼容从首页最近状态直接进入详情的场景
- 不破坏当前非列表入口

### 5.4 详情页是否要展示“返回列表”

当前判断：

- 首版不必新增额外按钮
- 直接复用现有“返回”按钮逻辑即可

原因：

- 只要返回动作足够稳定，就不必再增加界面负担

## 六、建议实现边界

### 6.1 前端修改内容

建议修改：

- `src/pages/MtmServiceCasesPage.vue`
- `src/pages/MtmServiceCaseDetailPage.vue`

### 6.2 列表页新增能力

列表页首版建议具备以下能力：

1. 首次进入时按 `route.query` 还原筛选状态
2. 搜索、状态筛选、分页变化时同步 URL
3. 刷新页面后保持同样查询结果
4. 浏览器前进后退时保持列表状态一致

### 6.3 详情页新增能力

详情页首版建议具备以下能力：

1. 从列表进入详情时保留最小返回上下文
2. 点击返回时优先回到带查询参数的列表页
3. 非列表入口进入详情时保持现有返回逻辑

---

## 七、风险点

### 7.1 路由监听与列表请求重复触发

如果本轮同时：

- 手动触发加载
- 又通过 `watch(route.query)` 再触发一次加载

容易造成重复请求。

因此需要明确“以谁作为数据加载触发源”。

### 7.2 查询参数不做合法化处理

如果直接信任 URL 中的：

- `page`
- `status`

可能出现非法页码或非法状态。

因此首版应增加最小解析与兜底逻辑。

### 7.3 返回逻辑误伤首页入口

如果详情页一律回列表页：

- 会破坏从首页最近状态进入详情的路径

因此必须保留来源判断。

---

## 八、当前结论

`T-P0-14` 最合理的最小范围确定为：

- `MTM 列表页与详情页之间的筛选联动 / 路由查询保持`

推荐实现方向：

1. 不新增后端接口
2. 只保留 `page`、`search`、`status` 三个核心查询参数
3. 列表页用路由查询参数作为可恢复上下文
4. 详情页返回优先回带查询条件的列表页
5. 以“可刷新、可回跳、可分享同一筛选结果”为本轮交付目标
