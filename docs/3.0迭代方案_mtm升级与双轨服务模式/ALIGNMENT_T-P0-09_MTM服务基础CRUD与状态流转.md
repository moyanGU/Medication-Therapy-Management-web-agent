# ALIGNMENT_T-P0-09_MTM服务基础CRUD与状态流转

## 一、原始任务

任务来源：`TASK_P0_正式拆分.md` 中的 `T-P0-09 MTM 服务基础 CRUD 与状态流转`

任务目标：

- 为 `apps.mtm` 提供最小可运行接口
- 支持服务单创建、列表、详情和状态流转

---

## 二、当前项目理解

### 2.1 现状判断

`T-P0-08` 已完成：

- 独立 `apps.mtm`
- 5 个最小模型
- 初始迁移
- 基础 admin

当前缺失的是：

- 面向前端和后续入口的正式 API
- 服务单最小状态流转接口

### 2.2 当前项目的真实使用场景

当前项目仍然以患者端为主，没有正式药师角色体系和药师工作台。

因此本轮更符合现状的最小方案是：

- 当前登录用户可以为自己发起 MTM 服务单
- 当前登录用户可以查看自己参与的服务单
- 状态流转先按最小串行流程控制

### 2.3 为什么不直接做完整通用更新

虽然 DRF 很容易一次性开放：

- `PUT`
- `PATCH`
- `DELETE`

但本任务只要求最小可运行流程。

如果现在直接开放完整更新：

- 会提前暴露大量尚未共识的字段编辑语义
- 会把问诊、评估、计划的编辑边界和服务单主状态混在一起
- 会让 `T-P0-10` 以后前端难以收敛到清晰入口

因此本轮更适合只做：

- 创建
- 列表
- 详情
- 单独状态流转 action

## 三、现有代码约束

### 3.1 接口组织约束

当前项目后端接口大体遵循：

- 每个 app 独立 `urls.py`
- 使用 DRF `DefaultRouter`
- 主要入口挂到 `backend/mtm_helper/urls.py`

因此本任务应新增：

- `backend/apps/mtm/serializers.py`
- `backend/apps/mtm/views.py`
- `backend/apps/mtm/urls.py`

并挂载到：

- `/api/mtm/`

### 3.2 响应结构约束

当前项目统一使用：

- `success_response`
- `error_response`
- 分页器统一结构

因此本任务必须保持：

- 成功响应：`{ success, message, data }`
- 分页响应：`data.results` + `data.pagination`

### 3.3 权限约束

当前项目没有成熟的药师角色与机构归属体系。

因此本轮权限不应做复杂角色授权，只做最小参与者范围控制：

- 当前用户作为 `patient`
- 或当前用户作为 `assigned_pharmacist`

可访问该服务单。

### 3.4 状态流转约束

`MTMServiceCase` 当前已固定状态：

- `pending`
- `interviewing`
- `assessing`
- `intervening`
- `following_up`
- `completed`

因此本轮应围绕这 6 个既有状态做流转，不再新增或改名。

## 四、需求边界确认

### 4.1 本任务要做什么

本任务负责：

- 服务单创建接口
- 服务单列表接口
- 服务单详情接口
- 服务单状态流转接口
- 基础序列化器
- 基础参与者访问控制
- 基础接口测试

### 4.2 本任务不做什么

本任务不负责：

- 问诊、评估、计划、随访的独立 CRUD
- 药师分配规则
- 复杂状态回退
- 审批流
- 删除服务单接口
- 前端入口页面

这些属于 `T-P0-10` 或更后续任务。

---

## 五、关键歧义与当前判断

### 5.1 服务单创建时 patient 怎么确定

当前判断：

- 创建时 `patient` 不从前端传
- 直接使用当前登录用户

原因：

- 当前项目是患者端主线
- 可以避免用户伪造为别人创建服务单

### 5.2 是否允许创建时直接指定药师

当前判断：

- 首版不作为必填项
- 字段保留但默认允许为空

原因：

- 现在没有正式药师分配体系
- `T-P0-10` 的用户主动发起场景也不依赖先选药师

### 5.3 列表范围如何定义

当前判断：

- 默认返回“当前用户参与的服务单”
- 条件为 `patient=request.user` 或 `assigned_pharmacist=request.user`

原因：

- 与当前角色体系不完整的现实相匹配
- 既兼容患者视角，也兼容未来最小药师视角

### 5.4 状态流转是否允许任意跳转

当前判断：

- 不允许任意跳转
- 只允许最小有序流转

建议规则：

- `pending -> interviewing`
- `interviewing -> assessing`
- `assessing -> intervening`
- `intervening -> following_up`
- `intervening -> completed`
- `following_up -> completed`

原因：

- 首版目标是“能追踪流程”，不是“支持复杂补录”
- 过早允许任意跳转会让后续统计和流程语义变脏

### 5.5 状态更新接口是否复用 PATCH

当前判断：

- 不复用通用 `PATCH`
- 使用独立 action

建议接口：

- `POST /api/mtm/service-cases/{id}/transition/`

原因：

- 更符合“动作接口”的含义
- 可以把状态校验集中处理
- 避免把状态更新和普通字段更新混在一起

## 六、建议接口边界

### 6.1 列表与创建

- `GET /api/mtm/service-cases/`
- `POST /api/mtm/service-cases/`

### 6.2 详情

- `GET /api/mtm/service-cases/{id}/`

### 6.3 状态流转

- `POST /api/mtm/service-cases/{id}/transition/`

请求体最小建议：

- `target_status`

可选补充：

- `notes`

### 6.4 详情返回内容

建议包含：

- 服务单主信息
- 问诊摘要
- 评估摘要
- 干预计划摘要
- 随访记录列表

目的：

- 让 `T-P0-10` 和后续最小前端入口能直接复用详情接口

---

## 七、风险点

### 7.1 过度开放字段编辑

如果把服务单做成完整通用更新接口：

- 很容易和后续问诊/评估/计划编辑职责冲突

### 7.2 状态流转规则过松

如果允许任意跳转：

- 后续流程统计和入口提示会失真

### 7.3 详情接口信息过少

如果详情只回服务单主表：

- 后续前端还得额外拼多接口
- 会削弱本轮“最小可运行”的价值

---

## 八、当前结论

`T-P0-09` 应采用“最小只读主线 + 单独动作流转”的策略。

推荐实现方向：

1. 新增 `serializers.py`、`views.py`、`urls.py`
2. 路由落到 `/api/mtm/service-cases/`
3. 只开放创建、列表、详情
4. 通过 `transition` action 处理状态流转
5. 列表和详情限制为当前参与者可见
6. 详情直接带回最小关联摘要
