# ALIGNMENT_T-P0-10_MTM最小入口与触发提示

## 一、原始任务

任务来源：`TASK_P0_正式拆分.md` 中的 `T-P0-10 MTM 最小入口与触发提示`

任务目标：

- 在首页加入真实可用的专业服务入口
- 让用户看到触发原因、手动发起服务并看到当前状态

---

## 二、当前项目理解

### 2.1 现状判断

当前项目已经具备：

- 首页聚合接口 `GET /api/dashboard/summary/`
- 首页已有 `mtm_entry_hint`
- `apps.mtm` 最小模型
- `T-P0-09` 提供的 MTM 服务创建/列表/详情/状态流转接口

当前真正缺的不是“再造一套 MTM 页面”，而是：

- 把首页的建议卡片从静态提示变成真实入口
- 让用户在首页直接完成最小发起动作
- 发起后看到服务状态

### 2.2 为什么首版不新建完整 MTM 工作页

虽然现在可以继续扩一个：

- `/mtm`
- `/mtm/:id`

但这会把任务从“入口与提示”扩成“页面体系”。

当前更符合任务边界的方式是：

- 保留首页卡片作为最小入口
- 在卡片内完成手动发起
- 在卡片内展示最近服务状态

这样可以最短路径打通：

- 风险提示
- 创建服务单
- 查看当前状态

---

## 三、现有代码约束

### 3.1 首页现状约束

当前 `DashboardPage.vue` 已经具备：

- `dashboard.mtm_entry_hint.recommended`
- `dashboard.mtm_entry_hint.reasons`
- `dashboard.mtm_entry_hint.message`

因此本任务应复用当前首页卡片，而不是重新设计另一套入口区。

### 3.2 后端规则现状约束

当前后端 `_build_dashboard_mtm_hint()` 已根据以下条件给出提示：

- 药品数量较多
- 近 7 天依从性偏低
- 存在到期复诊
- 风险提醒较多

因此前端不应另写一套和后端完全无关的判断，而应：

- 以前端展示首页聚合结果为主
- 仅在创建服务单时把当前提示上下文映射为最小创建参数

### 3.3 现有 API 约束

当前 `T-P0-09` 已有：

- `POST /api/mtm/service-cases/`
- `GET /api/mtm/service-cases/`

因此本任务不需要新增后端接口，首版应直接复用：

- 创建接口
- 列表接口

### 3.4 响应结构约束

当前项目前端必须正确处理双层数据结构。

因此本任务在对接分页列表和创建结果时，必须注意：

- 列表走分页结构
- 不能把 `response.data.xxx` 当成最终数据
- 需要按真实返回结构解包

---

## 四、需求边界确认

### 4.1 本任务要做什么

本任务负责：

- 首页 MTM 建议卡片增强
- 展示触发原因
- 接通真实 MTM 服务单创建
- 展示最近服务状态
- 防止重复连续发起
- 补基础前端类型/API 封装

### 4.2 本任务不做什么

本任务不负责：

- 独立 MTM 详情页面
- 独立 MTM 列表页面
- 问诊/评估/计划/随访编辑页
- 自动分诊
- 药师匹配

这些内容超出“最小入口与触发提示”的范围。

---

## 五、关键歧义与当前判断

### 5.1 入口放在哪里

当前判断：

- 入口继续放在首页现有“专业用药指导建议”卡片

原因：

- 这里已经具备风险上下文
- 用户不需要多跳一次页面
- 更符合最小入口任务

### 5.2 点击发起时创建什么样的服务单

当前判断：

- 调用 `POST /api/mtm/service-cases/`
- 默认由前端根据当前首页上下文生成最小 `trigger_source`
- `service_goal` 和 `notes` 用当前提示原因进行简要拼装

原因：

- 这样既不是空创建
- 也不需要额外表单打断首页操作

### 5.3 触发提示由谁负责

当前判断：

- 后端继续负责主判断
- 前端只负责展示和把当前上下文转成发起参数

原因：

- 避免前后端各写一套规则

### 5.4 已经有进行中服务时怎么办

当前判断：

- 首页显示“当前已有进行中的专业服务”
- 仍展示最近服务状态
- 默认不鼓励重复连续发起

原因：

- 避免用户一口气反复创建多条重复服务单

### 5.5 状态展示显示到什么程度

当前判断：

- 首页展示最近 1 到 3 条服务单摘要
- 至少显示：
  - 服务编号
  - 当前状态
  - 触发来源
  - 创建时间

原因：

- 足以满足“创建成功后的状态展示”
- 不会把首页做成完整工作台

## 六、建议实现边界

### 6.1 前端新增内容

建议新增：

- `src/types/mtm.ts`
- `src/api/mtm.ts`

并增强：

- `src/pages/DashboardPage.vue`

### 6.2 首页卡片建议能力

建议卡片具备以下能力：

1. 展示是否建议进入 MTM
2. 展示触发原因条目
3. 点击发起专业服务
4. 发起中有按钮 loading 态
5. 发起成功后立即刷新最近服务状态
6. 展示最近服务单摘要

### 6.3 最近服务摘要建议字段

建议至少展示：

- `case_number`
- `status`
- `trigger_source`
- `created_at`

并对进行中状态做强调显示。

---

## 七、风险点

### 7.1 重复创建

如果首页没有任何防重判断：

- 用户可能连续创建多条重复服务单

### 7.2 前端自行发明规则

如果前端重新写一套完全独立的触发条件：

- 会和首页聚合提示口径不一致

### 7.3 首页负担过重

如果试图在首页直接做完整 MTM 工作台：

- 会让任务范围失控
- 也会压缩当前首页的可读性

---

## 八、当前结论

`T-P0-10` 应采用“首页原地发起 + 最近状态展示”的策略。

推荐实现方向：

1. 复用首页现有 `mtm_entry_hint` 卡片
2. 接通真实 `create service case` 接口
3. 同时读取最近服务单列表
4. 首页展示最近服务状态与进行中提示
5. 不新建复杂 MTM 页面，不做复杂分诊
